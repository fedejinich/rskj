## Oracle and environment assumptions

- `jbmc/models/src/org/ethereum/crypto/Keccak256Helper.java:1-42,46-105` implements an ideal collision-free table of **16 distinct input messages per path**, and asserts if full. Default consistent mode assumes different digests for different inputs. `consistent=false` overapproximates all hashes; successes there do not rely on collision freedom. `concreteOutputs=true` fixes digest bytes to `c5 7a <index> 00...` and checks one consistent, collision-free assignment, not actual Keccak bytes. The model argues equivalence only where code treats digests as opaque copied/compared tokens. This is a modeling assumption, not a proof that Keccak cannot collide or that concrete hash outputs match production. `run-jbmc.sh:70-84,124-153` keeps unwinding assertions and the oracle/table assertion active; a timeout or failure of those assertions is never a property verdict.
- b6 uses concrete outputs for hash/store/Orchid/DTO checks (`HashHarness.java:20`, `StoreHarness.java:29,68,128`, `OrchidHarness.java:48,75`, `DtoHarness.java:15`). b7/b8 use concrete outputs for message comparison/history independence and the other hash-dependent checks (`OpsExtraHarness.java:30,219,250`, `HashHarness.java:104`). Node format and immutability use unconstrained outputs (`NodeHarness.java:135,152,170,182`, `OpsExtraHarness.java:56,88,111,168`). `models/README.md:5-51` explains substitutions; real trie, TrieKeyMapper and VarInt bytecode are not replaced. `jbmcenv/MemoryKeyValueDataSource.java:1-14,19-79` models HashMapDB, with a **16-entry** asserted capacity; its unsupported bulk methods throw. The project compares it against HashMapDB in `jbmc/models-test/run.sh`, but that differential check does not turn a 16-entry modeled store into an unbounded store. The table/DB limits remain bounded and resource stops remain unverified.
- Base-level negative controls already appear in the 644 leader results; `parser-total-neg` is staged on b6. They are not one negative control per split part. Compare the controls and invocation identity on each executor before accepting batch results.
