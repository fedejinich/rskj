## Two layers

* **Pure layer** (`Trie`, `Serialization`, `Ops`, `TrieStore`): caches that are functions of the
  node contents are not modelled (recomputed); nodes are immutable values. The main theorems
  (Proofs/, Obligations/) are stated here.
* **Operational layer** (`Operational.lean`, namespace `RskjTrie.Op`): every Java object carries
  its caches; each method returns its result *and the mutated receiver*, and callers thread the
  mutated objects in Java's evaluation order (e.g. `internalToMessage` calls `getChildrenSize`,
  the two `serializedLength`s, the two `isEmbeddable`s, the two `serializeInto`s, then the value,
  like Trie.java:677-739). Recursion is bounded by `OFUEL = 10^6` calls per operation (exhaustion
  is an error, never silent; the runner prints it as `error`, and every differential output
  matches Java's). `trie-diff` runs this
  layer.
* **Bridge** (`Proofs/Bridge.lean`, `Proofs/BridgePut.lean`): `OTrie.Rep env o t` — the
  operational object `o` represents the resident pure trie `t` (same fields; every cache unset or
  equal to the pure encoder's value; a child is either represented or is a hash reference to a
  *non-embeddable* child whose message and subtree are in the store). Proved: `readOK` (every
  read method: the pure value or fuel exhaustion, receiver still represented), `getRec_Rep`
  (`get`), `putOK`/`put_bridge` (`put`/`delete`/`deleteRecursive` fail exactly when the pure ones
  fail, else return a representation of the pure result; the pure results stay resident and
  cache-consistent), `ops_bridge` (any `put`/`delete` sequence from `new Trie()`: operational
  `getHash`/`toMessage`/`get` = pure ones), `retrieve_bridge` (after the pure `save` of a
  well-formed trie, operational `retrieve` gives a represented object, whose reads equal the pure
  reads of the retrieved node, and on which `put_bridge` applies). Not bridged: the operational
  `save` itself (differential only), `MultiTrieStore`, TRIE-HASH-04's crafted store (excluded by
  `Rep` by design; the two layers differ there, which is the finding).

`Trie` and `NodeReference` are mutually dependent in Java; their store- and serialization-dependent
methods live together in `Serialization.lean`.

## Hash assumptions

`trie_hash_03` assumes 32-byte hash outputs and collision freedom only on the finite list
of messages and values in the two compared tries, plus the empty-root input `80`.
It does not assume global injectivity from arbitrary byte strings to 32-byte digests,
which is impossible. This is an ideal-hash hypothesis, not a theorem about real Keccak.

## Operational layer: aliasing

Java shares objects between the old and the new trie after `put` (the new node references the
old children). The operational layer holds each object once, as a value inside the trie the
runner holds, so a cache written *through the old trie* into a shared object is not seen by the
new trie (and vice versa). Java writes caches through the old trie during `put` in
`referenceSize` of the replaced child (Trie.java:901/908) and in `retrieveNode` (lazy loads).
This only changes output when a later load changes an embedding decision, i.e. on crafted stores
where a hashed child is embeddable (outside `Rep`); on represented objects every cache equals
the pure value, so where it is written is not observable (`putOK`, `readOK`). The runner keeps
only the trie returned by `put`/`delete` (the old trie is not used afterwards).

## Failed `load` / `reload`

Java's runner calls `store.retrieve(hash).orElseThrow()` (DiffRunner.java:95, :97): a missing root
throws `NoSuchElementException`, which is not caught, so the Java run aborts. The Lean runner
prints `load error` / `reload error` and keeps the previous trie. No case file contains a failing
`load`/`reload`; such a case would be reported as a difference.

## Differential status

`differential/run.sh` (operational layer): all five case files are byte-identical to Java
(decode 1, keymap 1, random 300, reproducers 7, unitrie 100 cases). With `trie-diff --pure`
the only difference is `reproducers.cases` / `repro-hash-04-loaded`: after `getk 00` loads the

## Other models (phase B)

* `MultiTrieStore` (MultiTrieStore.java:42-150): epochs newest first as `List DB`; `save`/
  `saveValue` write to epoch 0; `retrieve`/`retrieveValue` search newest first; `collect` retrieves
  the root (marked saved), saves it into the second-oldest epoch (a no-op, see above), drops the
  oldest, rotates, adds a fresh epoch. The `OnEpochDispose` callback and `HashMapDB.close` are not
  modelled.
* `MutableRepository.setupContract` (MutableRepository.java:105-109): writes
  `ONE_BYTE_ARRAY = [0x01]` (:56) at `getAccountStoragePrefixKey(addr)`.
* RSKIP112 type bytes: nothing to model — `put` stores the value bytes as given (TRIE-KEY-10).
* `TrieDTO` (TrieDTO.java:79-470): only `decodeFromMessage(src, ds)` (no preloading, no hash
  check) and `toMessage()`; the "sync" encoding built while parsing (embedded children with a
  `Uint24` length, long values inline) is `encoded`.
